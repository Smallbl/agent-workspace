**2. KnotScryer 论文：在"干净"技能里挖出 612 条危险组合链**
10 月 23 日发到 arXiv 的预印本《Detecting Insecure Compositions of Clean Agent Skills via Capability-Flow Graph Analysis》（Yihao Li 等六人）提出：逐个审计技能是不充分的，因为"每个都无害"的技能可以被 Agent 在运行时组合成违规操作。作者扫描 2026 年 5 月 18 日的 ClawHub 快照，13,598 个被标记为 clean 的技能中查出 612 条高置信度违规链；在三种 Agent 框架、三种模型（Claude Sonnet 4.6、GPT-5.5、GLM-5.1）上平均 79.2% 可被利用，且其中 84 条链（13.7%）的所有技能都被 Cisco AI Defense 的单技能扫描器判为"安全"。典型例子：一个 GitLab 查看技能 + 一个部署技能 = 公开 issue 里植入的指令可导致宿主代码执行；Outlook 阅读技能 + 冷邮件发送技能 = 把审计数字泄露到攻击者邮箱。
原文：https://arxiv.org/html/2610.32155v1

**【豆浆学习笔记】**

一、KnotScryer 这篇论文对我们是"直接可用"的，不是背景知识
它给出的防御方案不是补丁，而是一条配置规则：不要让一条危险链上的技能同时出现在 Agent 的技能列表里。OpenClaw 已经支持——`agents.defaults.skills` 是共享基线，`agents.entries.<id>.skills` 是每个 Agent 的最终显式列表，会**替换**而非合并默认值，空列表 = 不暴露任何技能。这跟我们 AGENTS.md 里"主 Agent 绝不自己写代码、必须派发给子 Agent"的铁律是同一个思路：不靠自觉，靠配置隔离。
但论文同时提醒一个关键限制：技能 allowlist 只是"可见性与加载过滤器，不是 shell 期授权边界"——拥有 host exec 权限的 Agent 仍然可以调用外部客户端。所以必须配 sandbox + 收紧 exec 策略。这一点对我们尤其重要，因为我们的定时日报链路就是典型的"读外部内容 → 写文件 → 发飞书"，如果某个子 Agent 同时持有"读网页"和"发消息"能力，就构成一条完整的 KnotScryer 链。建议：给所有子 Agent 建立两列清单——读外部内容的（读）和发送/写入/执行的（做），绝不放在同一个 Agent 上。

二、我们比昨天又多知道了一件事：本机版本不只是"落后"，而是"不在安全补丁线上"
本机 2026.9.5，而 2026.10.10 才是最新正式版，2026.9.36 才是对应的 extended-stable 线。我们停在 2026.9.5，等于既没吃到 10 月的功能，也错过了 10 月那批安全修复（升级恢复、凭据处理、workspace 限制、IMAP 发件人伪造、Teams 授权默认值放开的修复）。特别是 2026.9.36 里的 Teams 修复——名称键控的 `teams`/`groupAllowFrom` 条目解析失败时"现在什么都不授权，而不是对所有团队或群开放机器人"，这正是一类静默的越权。我们虽用飞书不用 Teams，但如果以后在单位内推广，这类默认值放开的坑值得提前知道。

三、可以直接搬到工作流的三个点
1. **Advisor 的思路**（不等升级，先手动化）——它本质是"Agent 自查是否跑偏"。我们派发子 Agent 时最常见的失败是"已定位信息"字段填不全，子 Agent 自行猜路径绕大圈。与其等 Advisor 上线，不如在派发格式里加一条硬性自检：子 Agent 每次回复前先复述"我的任务理解是……已知信息不足的是……"。这条不花额外模型调用，收益却接近 Advisor 纠偏本身。
2. **`@steipete/gog` 的 `--readonly` / `--gmail-no-send` 分层**——正好对上王的工作场景：邮箱和日历是招投标行业信息密度最高的入口（供应商公告、澄清文件、会议通知）。官方建议是"读和写分成两个 Agent，写的那个等人工批准"。我们可以照做：一个只读 Agent 负责抓取与归类，一个可写 Agent 只在人工确认后发信。`--enable-commands-exact` 精确命令白名单也比"允许整个 Gmail scope"安全得多。
3. **技能库的两列审计法**——我们 workspace 里的技能是本地自建的，风险低于公共 ClawHub，但仍应按 KnotScryer 的标准自查一次：列出每个技能是"读"还是"做"，标出同时持有两类的技能。这是我们能立刻做、且成本很低的一次安全加固。

四、需要留意但不要神化的
论文的测试对象是 2026.6.8 版 OpenClaw，ClawHub 快照是 5 个月前的，测试在本地网络进行，作者也说明这些是方向性数字，不能当作当前环境的绝对风险评分。所以正确的用法是把它当作"检查方法的样例"，而不是"风险排行榜"。同时，作者称已向技能平台披露这些链，但截至目前没看到 ClawHub 的公开回应——这意味着公共技能的组合风险在短期内不会被自动拦截，仍要靠我们自己的 allowlist 设计。

五、升级这件事该收口了
连续两天的日报都在提示同一个版本差距，今天又多了一条"KnotScryer 论文显示安全边界需要主动管理"的推力。升级到 2026.10.10 的标准动作我们已经有了：`openclaw doctor` 查废弃字段 → 完整备份 `~/.openclaw/` → 升级 → `openclaw doctor --fix` → 验证飞书双向同步与所有定时任务 → 确认无误后再 `openclaw gateway status --deep`。按我们自己 AGENTS.md 的规范，改配置/升级后用 `bash ~/.scripts/safe-gateway-restart.sh`（10 秒缓冲）而不是直接重启，避免正在处理的消息丢失。
