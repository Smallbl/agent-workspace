beta 线首次引入一等公民的「知识捕获」能力——Knowledge Scribes 让每个 Agent、每条会话和 Control UI 都能沉淀并复用可复用的书记式工作流；同批还加入了以 PostgreSQL 为后端的状态存储、迁移工具与兼容性覆盖（官方 changelog 标注由 steipete 撰写）。这两项指向同一个问题：当会话数、Agent 数、项目档案继续增长，文件系统和 SQLite 会成为瓶颈——前者解决"知识怎么沉淀成可复用流程"，后者解决"状态往哪儿放"。对多项目并行、强调记忆持久性的团队，这两条是本轮最有想象力的方向。

四、版本事实修正：Node 门槛按版本不同，engines 与安全地板要分开看
逐版本实测 `npm view openclaw@<V> engines.node`：
- 2026.11.1 → `>=24.16.0 <25 || >=26.1.0`
- 2026.10.10 → `>=24.16.0 <25 || >=26.1.0`
- 2026.11.5-beta.1 → `>=24.16.0 <25 || >=26.1.0`
- 2026.9.36（extended-stable） → `>=24.22.1 <25 || >=26.12.1`
这纠正了昨日简报中的说法："需要 24.22.1+/26.12.1+ 才能升级"其实是 extended-stable 线 2026.9.36 的 engines 门槛，主稳定线 2026.11.1 的准入门槛是 24.16+/26.1+。本机 Node v26.7.0 满足 2026.11.1 的 engines 准入门槛，但不满足 2026.9.36 的门槛。至于"在旧 Node 上拒绝安装/执行"：2026.11.1 release notes 中只找到原文 "Checks the target Node requirement before staging Git updates when the running updater supports the check."，没有"拒绝安装"的明文表述，因此不作此断言；engines 才是 npm 的硬性准入条件。

【豆浆学习笔记】

一、昨日到今日最重要的认知修正
Node 门槛不是全局一刀切，而是分版本写进 engines 的。2026.11.1/2026.10.10/2026.11.5-beta.1 都是 `>=24.16.0 <25 || >=26.1.0`，只有 extended-stable 2026.9.36 抬到 `>=24.22.1 <25 || >=26.12.1`。所以"升级前必须先升 Node"这个结论只在选 LTS 线时成立；我们本机 Node v26.7.0 已经满足主稳定线的 npm 准入门槛，升级 2026.11.1 在 npm 层面不会被拒。engines 是 npm 会不会拒绝安装的硬条件，和"Node 安全公告建议的修复版本"是两件事，别混着说。

二、配置热更新：不能说"不再需要重启"
我在 2026.11.1 的 npm 包里 grep 到了运行时 reload 的 outcome 字符串：`applied`（配置已在运行中的 Gateway 生效）、`restart-pending`（候选已就绪、等待重启）、`applied-restart-required`（运行时提交失败后已安排一次恢复性重启）。也就是说，热路径存在但不是无条件——异常路径依然会回到重启。结论只能写成"配置可在运行中的 Gateway 内应用，失败路径会回落到需重启状态并自动安排恢复重启"，不能写成"不强制重启/不再丢消息"。我们 AGENTS.md 里的安全重启脚本应继续保留作为兜底。

三、对我们最直接的可用项
1. Agent 目录清理：doctor 明确点名 agent-frontend、backend-agent 是孤儿目录。它们虽然有历史 session，但配置层已经不认识了——留着会持续在 doctor 报告里制造噪音，也容易让人误以为这两个 Agent 还能被派发。建议二选一：补回 agents.entries 条目，或在确认不再需要后移走目录。这条需要王确认后再动。
2. Session SQLite 迁移：1354 个历史 session issue + 1377 条 legacy 元数据，说明我们还在用旧存储路径，检索与迁移可靠性会受影响。`openclaw doctor --fix` 可以迁移，但按经验迁移前必须先备份 `~/.openclaw`，且不要在有活跃会话时跑。
3. 飞书密钥迁移到 SecretRef：doctor 明确点名 channels.feishu.accounts.main.appSecret 与 zhanling 两个 appSecret 是明文。这跟我们 "secrets" 工具的能力正好对得上，可以把 appSecret 迁到受保护存储，之后审计日志里就不会再出现明文。
4. command owner 未配置：目前 /update、重启、改配置这些高权限动作没有可信操作员绑定。这既是安全缺口也是流程缺口——建议把王的飞书账号设为 commands.ownerAllowFrom，让权限有明确归属。

四、值得试的新特性
1. Knowledge Scribes（beta）：可以理解为"跨 Agent 的知识沉淀工作流"。对我们的招投标行业场景（招标文件范本、资格条件模板、答疑口径库）几乎是为量身定做的概念，值得在 beta 转正后优先评估。
2. 对话内 PR 工作流（beta）：和 AGENTS.md 的"主 Agent 绝不自己写代码"铁律天然配套——主 Agent 在会话里发起 PR，把 diff 交给人和评审流程，正好解决"主 Agent 想写代码"的越界风险。
3. Automations 持久化流（beta）：我们所有定时简报都靠 cron 的 agentTurn，目前每次跑都是一次性上下文。持久化流如果能让定时任务保留连续上下文，对"跨天跟进项目进度"是明显加分。
4. Control UI 移动端重构（beta）：老板如果需要在手机上追项目进度，改版后的体验值得试。

五、风险提示
2026.11.1 起 doctor 的退出码语义变了（受阻或修复未完成返回非零）。我们如果有巡检脚本在解析 doctor 输出，需要更新判断逻辑，否则会把"真失败"继续当成"通过"——这正好是上一版修的"假成功"问题的反面影响面，升级当天务必复核脚本。

六、一句话结论
今天真正的增量是 beta 线 2026.11.5-beta.1：知识沉淀（Knowledge Scribes）、PostgreSQL 状态层、对话内 PR、持久化定时流，这四件事直接对着我们"多项目并行 + 记忆持久 + 铁律不越界"的痛点。但 beta 不该急着上生产——今天更该做的是把本机的三个确定性问题清掉：孤儿 agent 目录、1354 个 session SQLite issue、飞书明文密钥，以及把 command owner 配上。
