## 候选主题评估

### ✅ 候选 1：10-24"三份 cron 简报未生成"是误判 —— 三个任务都是工作日调度（第 105 条）

- **长期误报的来源**：10-25 起连续 4 个周期把"10-24 三份简报未生成"记为待排查故障，写进了「📌 下次注意」第 30 条、`05-系统稳定性` 与 `11-故障记录`。
- **实测反证**：`cron_jobs` 里三个简报任务的 schedule 是 `1-5`（周一至周五），**10-24 是周六、10-25 是周日** → 本来就不该有产物。
- **重新核算 10-12 ~ 11-01 的缺口**：

  | 任务 | 缺失的**工作日** | 缺失的周末（预期） |
  |------|----------------|-------------------|
  | ai-morning-briefing | **10-12（周一）** | 10-17/18、10-24/25、10-31、11-01 |
  | ai-evening-briefing | **10-16（周五）、10-21（周三）** | 10-17/18、10-24/25、10-31、11-01 |
  | ai-work-briefing | **10-22（周四）、10-27（周二）** | 10-17/18、10-24/25、10-31、11-01 |
  | openclaw-daily-news | 无 | 11-01（尚未到 09:00） |

- **结论**：真正的"工作日缺产物"只有 5 天，属于**当天任务偶发失败**（可从该日 cron run 记录回溯），而不是"三个任务都坏了"。原待办应关闭，改为按 5 个具体日期逐个查。
- **方法论教训（写入本条）**：**先看 schedule 再谈缺口** —— 连续 4 个周期没人去读 cron 的 `expr`，把"周末不跑"当成了"任务故障"。

### ✅ 候选 2：11-01 首轮失败的真因是上游 429 + provider 级 idle timeout，不是 agent 超时（第 106 条）

- 前 4 个周期的首轮失败诊断写的是"`agents.defaults.timeoutSeconds` 偏小"（记于 `05-系统稳定性`），本周期拿到 Gateway 日志后**这条诊断需要修正**：11-01 03:00 的失败链是
  `429 server is busy`（等 100s）→ `LLM idle timeout (120s)` → `failing over` → `No further authorized account for this provider` → 整轮 error。
- **两点关键含义**：
  1. **provider 级 120s idle timeout 与 agent 级 timeoutSeconds 是两套东西** —— 把 `agents.defaults.timeoutSeconds` 从 600 提到 1800，对这次失败**无效**。
  2. **本机没有故障转移通道** —— `auth.profiles` 只有 `minimax:cn` 一个，`auth.order` 为空 → 429 或超时时没有第二个账号可切，**直接整轮失败**（此前多轮记录的 "No further authorized account for this provider" 就是这个）。
- **可执行结论**：要真正兜底，必须补一个**备用 provider 或备用 auth profile 并写进 `auth.order`**，而不是继续调 agent 超时。
